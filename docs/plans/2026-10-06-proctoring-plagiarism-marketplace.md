# План реализации: прокторинг, антиплагиат решений, развитие второй механики

> **Для исполнителя:** план рассчитан на реализацию задачами по 2–5 минут работы каждая,
> с тестом на каждое поведение и коммитом после каждой задачи.

**Цель:** закрыть три направления развития платформы — устойчивость теста к прохождению
«со знающим другом», проверку самостоятельности решений и масштабирование обратной
механики (шаблоны потребностей, авторазбор описаний, массовые публикации).

**Архитектура:** три независимых эпика поверх существующей архитектуры. Прокторинг
расширяет уже работающий контроль времени в тестировании и выносит правила в отдельный
сервис чистых функций. Антиплагиат добавляет нормализацию кода (токены + структурный
отпечаток AST) и таблицу совпадений между решениями. Вторая механика расширяет кабинет
работодателя шаблонами потребностей, разбором свободного описания в структуру и
пакетной публикацией вакансий.

**Стек:** Python 3.12 · FastAPI · SQLAlchemy 2 (async) · Alembic · PostgreSQL 16 ·
pytest + httpx · React 19 + TypeScript · локальная модель через Ollama.

**Что уже есть (не переделываем):**
- `ItemResponseRecord.response_time_ms` — время ответа пишется с самого начала;
- `TestSession.warnings` — текстовые предупреждения сессии;
- `testing_flow.py:53` `FAST_ANSWER_MS = 1500` и проверка на `:217` — первый признак
  (быстрый ответ на сложное задание) уже реализован;
- `Item.max_exposure` / `exposure_count` — контроль показов банка;
- `services/ai.py` — черновик потребности (`/ai/need/draft`) уже строит структуру из текста;
- `RegularTask` / `TaskSubmission.solution` — решения кандидатов уже сохраняются текстом;
- `EmployerNeed`, `create_need`, `create_vacancy`, `create_task` — точки расширения.

## Эпик A. Прокторинг и детекция аномалий прохождения

**Результат эпика:** сессия тестирования получает отчёт с признаками, каждый признак
хранит доказательство; работодатель не видит флаги как обвинение, администратор и
кандидат — видят.

### A1. Вынести параметры прокторинга в конфигурацию

**Файлы:** `backend/app/core/config.py`, `.env.example`, `backend/app/services/testing_flow.py`

**Шаги:**
1. Добавить в `Settings`: `proctoring_enabled: bool = True`, `fast_answer_ms: int = 1500`,
   `fast_answer_min_difficulty: float = 0.5`, `min_viable_answer_ms: int = 300`,
   `uniform_timing_tolerance_ms: int = 300`, `proctoring_flag_threshold: int = 2`.
2. В `.env.example` добавить блок с комментариями (что означает каждый параметр).
3. В `testing_flow.py` заменить локальную константу `FAST_ANSWER_MS` на значение из настроек.

**Проверка:** `env -u PYTHONPATH .venv/bin/python -m pytest -q` — 287 тестов проходят.

### A2. Сервис правил прокторинга

**Файлы:** создать `backend/app/services/proctoring.py`; тест: `backend/tests/test_proctoring.py`

**Шаги:**
1. Написать падающий тест: нормальное прохождение не даёт флагов.

```python
def test_normal_run_has_no_flags():
    responses = [Response(correct=True, response_time_ms=9000, difficulty=0.2)] * 8
    report = proctoring.analyze(responses, settings=proctoring.Settings())
    assert report.flags == []
```

2. Реализовать минимально:

```python
@dataclass(frozen=True)
class Flag:
    code: str            # fast_hard_answer | sub_minimum | uniform_timing | pattern_guess
    severity: str        # low | medium | high
    detail: str          # человекочитаемое объяснение
    evidence: dict       # сырые числа — доказательство, а не оценка

@dataclass(frozen=True)
class Report:
    flags: list[Flag]
    score: float         # 0..1, доля сработавших признаков

def analyze(responses, *, settings) -> Report: ...
```

3. Правила (каждое — отдельный тест):
   - `fast_hard_answer` — ответ на задание сложности выше порога быстрее `fast_answer_ms`
     (перенос существующей проверки);
   - `sub_minimum` — время ответа меньше `min_viable_answer_ms` (физически невозможно
     осознанно прочитать и ответить);
   - `uniform_timing` — разброс времени ответов меньше допуска при 5+ ответах
     (признак автоматического ввода); evidence: σ и список времён;
   - `pattern_guess` — серия одинаковых индексов ответа на сложных заданиях.
4. Тесты на негативные случаи: флаг не ставится, если данных нет (время не передано),
   если ответов меньше минимума для правила.

**Проверка:** `pytest tests/test_proctoring.py -v` → все тесты проходят.

## Эпик B. Антиплагиат решений (токены + отпечаток AST)

**Результат эпика:** работодатель видит не «копия», а «совпадение 87% с решением другого
кандидата по этому заданию» с доказательством — что именно совпало.

### B1. Тип задания и язык

**Файлы:** `backend/app/models/marketplace.py`, `backend/app/schemas/marketplace.py`,
миграция `20261007_0010_task_code.py`

**Шаги:**
1. `RegularTask.task_type` (`text` по умолчанию | `code`), `RegularTask.language`
   (`python` | `javascript`, nullable).
2. `TaskSubmission.language` — язык решения (наследуется от задания).
3. Миграция `0010` (`down_revision = "20261007_0009"`).
4. Тест: создание задания с `task_type="code"` через API.

### B2. Нормализация и сравнение

**Файлы:** создать `backend/app/services/plagiarism.py`; тест `backend/tests/test_plagiarism.py`

**Шаги (каждая функция — со своим тестом):**
1. `normalize_tokens(code, language) -> list[str]`: убрать комментарии и строковые
   литералы, привести к нижнему регистру ключевые слова, схлопнуть пробелы; для Python —
   `tokenize` из стандартной библиотеки, для JS — регекс-токенизатор.
2. `ast_fingerprint(code, language) -> str`: для Python — `ast.parse` и структурный
   отпечаток обхода (последовательность типов узлов без литералов и имён), затем хэш;
   для JS при отсутствии парсера — отпечаток по структуре скобок и ключевых слов.
   Назначение: устойчивость к переименованию переменных.
3. `similarity(a, b) -> float`: `0.6 × Jaccard(shingles(токены, k=4)) + 0.4 × доля
   совпавших поддеревьев AST`. Диапазон 0..1.
4. `find_pairs(submissions) -> list[Pair]`: попарное сравнение внутри задания, порог
   `plagiarism_threshold = 0.7`, лимит пула 200 решений, минимальная длина 40 токенов
   (короткие решения не сравниваем — ложные совпадения).
5. Невалидный код не ломает разбор: сохраняем `parse_error=True`, пара не обвиняется.

**Тесты:**
- копия с переименованием переменных и добавленными комментариями → ≥ 0.7;
- независимое решение той же задачи → < 0.3;
- форматирование и пустые строки не влияют на балл;
- синтаксически неверный код → `parse_error`, исключения нет.

## Эпик C. Вторая механика: шаблоны, авторазбор, массовые публикации

## Сквозные требования

1. **Миграции:** `0009` (прокторинг), `0010` (код + совпадения), `0011` (шаблоны);
   каждая с `upgrade`/`downgrade`, проверка `alembic upgrade head` на чистой базе.
2. **RBAC и OpenAPI:** каждый новый эндпоинт — своя роль, `summary`, запись в схему.
3. **Честность формулировок:** флаг прокторинга и совпадение кода — признаки, не
   приговор; в интерфейсе «требует внимания», решение принимает человек.
4. **Персональные данные:** флаги прокторинга работодателю не показываются; совпадения
   доступны только владельцу задания и только агрегированно.
5. **Числа в документации** обновляются после каждого эпика (тесты, методы API, миграции).
6. **Тесты:** каждый эпик добавляет не менее 8 тестов; итоговое покрытие не ниже 95%.
7. **Коммиты:** после каждой задачи, сообщение по существу (что и зачем), русский язык.

## Риски и как закрываем

| Риск | Ответ |
|---|---|
