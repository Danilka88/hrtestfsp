# 04. Концепция: защита от фиктивных вакансий и интеграция с ATS

Раздел соответствует требованию «за рамками MVP, но важно для дальнейшего развития»:
ожидается **концепция и архитектурный подход**, а не рабочая реализация.

---

## 1. Защита от фиктивных вакансий и недобросовестных работодателей

### Проблема
«Призрачные» вакансии публикуют без реальной потребности в найме (по отдельным
оценкам — до трети объявлений), а часть объявлений размещают мошенники. Для
платформы это прямая потеря доверия: кандидат перестаёт реагировать, и механика
обратного подбора теряет смысл.

### Слои защиты (от дешёвых к дорогим)

| Слой | Мера | Стоимость | Эффект |
|---|---|---|---|
| 1. Обязательные данные | ЗП указывается обязательно и в вакансии, и в приглашении *(уже в MVP)* | нулевая | отсекает «вакансии-заглушки» без условий |
| 2. Верификация компании | подтверждение домена корпоративной почты, ИНН/ОГРН, сверка с открытыми реестрами | низкая | отсекает анонимных «работодателей» |
| 3. Поведенческие метрики | доля ответов на отклики, конверсия приглашение→принятие, время реакции, доля отказов после контакта | низкая | выявляет работодателей, которые собирают контакты без найма |
| 4. Автоматические эвристики | дубликаты объявлений, шаблонные описания, всплеск публикаций, несоответствие ЗП рынку | средняя | ловит массовый спам |
| 5. Ограничения и «срок годности» | лимит активных вакансий без ответов; обязательное подтверждение актуальности раз в N недель | низкая | гасит «вечные» объявления |
| 6. Репутация и жалобы | публичный скоринг работодателя, жалобы кандидатов с ручной проверкой | средняя | долгосрочный эффект |
| 7. Ручная модерация | выборочная проверка по триггерам риска | высокая | финальный барьер |

### Архитектурный подход
- Отдельный модуль `moderation` со **скорингом риска** (`risk_score` по работодателю и
  по вакансии), работающий как **асинхронный потребитель событий**: публикация
  вакансии, отправка приглашения, отклик.
- Скоринг — за интерфейсом `RiskScorer` (правила сейчас, ML позже), поэтому MVP не
  усложняется: сегодня это заглушка, возвращающая нейтральный балл.
- Решения модерации **аудируются** и обратимы: скрытие вакансии, ограничение
  приглашений, запрос верификации.
- **Принцип невиновности по умолчанию**: ни одна эвристика не блокирует аккаунт
  автоматически без человека в контуре.

### Что уже заложено в MVP
- Обязательная ЗП в вакансии и в приглашении.
- Статусы приглашений и откликов — источник поведенческих метрик.
- Раскрытие контактов только по согласию кандидата (принятие/отклик) — снижает
  ценность платформы для «сборщиков контактов».
- Провайдерский слой (`providers/`) — точка подключения реальных проверок.

## 2. Интеграция с ATS работодателей

### Проблема
У крупных работодателей найм уже живёт в ATS. Если платформа — отдельный остров,
рекрутер будет вести двойной учёт и уйдёт.

### Модель интеграции
**Двусторонняя, событийная, идемпотентная.**

Исходящие события (платформа → ATS):

| Событие | Когда | Полезная нагрузка |
|---|---|---|
| `candidate.invited` | отправлено приглашение | ссылка кандидата, категория (специализация × грейд), ЗП, идентификатор приглашения |
| `invitation.accepted` / `invitation.declined` | решение кандидата | идентификатор, время |
| `contact.revealed` | раскрытие контактов | контакты, основание (принятие или отклик) |
| `application.created` | самостоятельный отклик | ссылка кандидата, вакансия |

Входящие (ATS → платформа): обновление статуса найма (`hired`, `rejected`),
синхронизация справочника вакансий.

### Технические принципы
1. **Webhook-подписка + REST-push.** Работодатель регистрирует endpoint; платформа
   шлёт события с подписью **HMAC-SHA256** и заголовком `X-Idempotency-Key`.
2. **Доставка «хотя бы один раз»** с экспоненциальной задержкой и «мёртвой» очередью;
   получатель обязан дедуплицировать по ключу идемпотентности.
3. **Разделение по адаптерам**: `AtsAdapter` — интерфейс (как `providers/` в MVP),
   конкретные реализации под конкретные ATS. Ядро о событиях не знает.
4. **Очередь и ретраи** — Redis/брокер (в MVP Redis уже есть), без блокировки
   пользовательских запросов.
5. **Ориентация на HR Open Standards** для схем обмена, чтобы не изобретать формат.
6. **Аудит и согласие**: передача данных кандидата в ATS возможна только в рамках
   уже данного согласия; события логируются.

### Что уже заложено в MVP
- Интерфейсы провайдеров и единая точка подмены реализаций.
- Статусная модель приглашений/откликов — готовая модель событий.
- Аудит-точки (факт согласия, время раскрытия контактов).
- Redis в инфраструктуре — готовая база для очереди событий.

## 3. Дорожная карта

| Этап | Содержание |
|---|---|
| Сразу после хакатона | верификация домена работодателя, метрики поведения, «срок годности» вакансий |
| Ближайшее развитие | `moderation` со скорингом риска, жалобы, аудит решений |
| Средний срок | `AtsAdapter` для 1–2 популярных ATS, webhook-подписки, дедупликация |
| Дальше | ML-скоринг риска, HR Open Standards, синхронизация вакансий и статусов найма |

Смысловая рамка: **сначала дешёвые барьеры (данные и поведение), затем дорогие
(модерация и ML)** — так платформа остаётся работоспособной на каждом шаге.
