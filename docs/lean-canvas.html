01Проблема

Универсальные площадки исчерпали ресурс: издержки несут обе стороны, результативность подбора минимальна.

1Работодатель

Вручную фильтрует сотни нерелевантных откликов силами дорогих специалистов. Формальное резюме фиксирует стек и места работы, но не подтверждает практическую компетентность — отбор сводится к совпадению ключевых слов.

2Кандидат

Откликается вслепую и не получает обратной связи. Отраслевая специфика — стек, грейд, роль в команде, формат работы — на универсальных платформах не формализована.

3Рынок ИТ

Вал нерелевантных откликов при дефиците опытных профи, которые не сидят на классических job-сайтах: нехватку нужных навыков отмечают 93% компаний, в ИТ — 64%.1312

02Два ядра решения

Смысловой центр продукта — механика, принципиально отличная от прямого отклика кандидата на вакансию.

AМеханика тестирования

Категория определяется не резюме, а обязательным путём при регистрации.

Опрос по отрасли и специализации→ Выбор предполагаемого грейда→ Тест на заявленный грейд→ Авто-присвоение категории

Категория = специализация × грейд (например, «бэкенд с опытом», «фронтенд до года»). Внутри категории кандидаты ранжируются по силе профиля.

BОбратная механика подбора 35% оценки

Инициатива у работодателя — ориентир модели LHH «работа находит человека».

Потребность работодателя→ Подборка категорий и кандидатов→ Приглашение с указанием ЗП→ Принятие → раскрытие контактов

Приглашение — без обязательной привязки к вакансии. Контакты кандидата раскрываются только после принятия или самостоятельного отклика.

03Lean Canvas

Классическая сетка Эша Маури; блоки, критичные для хакатона, выделены.

Problem

  • Работодатель тратит дорогое время на вал нерелевантных откликов; нет объективного сигнала о компетентности
  • Кандидат откликается вслепую, без обратной связи
  • ИТ-специфика не формализована на универсальных площадках

Solution

  • Обязательный путь: опрос → грейд → адаптивный тест → категория
  • Обратный подбор: подборка → приглашение с ЗП → раскрытие контактов по согласию
  • Верифицированный профиль + регулярные короткие задания

Unique Value Proposition

  • Работодатель находит уже подтверждённую категорию и сам приглашает — с зарплатой сразу, без вала резюме
  • Кандидат получает приглашения, а не откликается вслепую
  • Верификация = тест + подтверждённые достижения

Unfair Advantage

  • Данные и бренд Федерации спортивного программирования
  • Объективные результаты соревнований как эксклюзивный сигнал
  • Нет у универсальных площадок29

Customer Segments

Key Metrics

  • Стабильность грейда при повторном тесте
  • Дискриминативность заданий

Channels

  • Партнёрство с сообществами и соревнованиями

Cost Structure

05Механика тестирования: решаем противоречие

Единый набор заданий быстро расходится по рынку. Генерация «на лету» под каждого не гарантирует сопоставимую сложность. Решение — гибрид «параметрическая генерация + калибровка + адаптивность».

1Параметрическая генерация

Задание описывается шаблоном и параметрами. Из шаблона рождается уникальный вариант, но сложность задаётся параметрами, а не текстом.7

2Адаптивная выдача (IRT)

Оценка способности θ обновляется после каждого ответа; следующее задание выбирается как максимизирующее информацию.67

3Контроль показов (exposure)

Лимит показов и счётчик у каждого задания, ротация версий, взвешенный отбор — защита от «расхождения заданий по рынку».9

4Детекция компрометации

Мониторинг баллов и времени ответа в реальном времени выявляет «слитые» задания и ответы по предзнанию.68

5Анти-плагиат кода

Для задач с кодом — сравнение по нормализованным токенам/AST между сессиями.26

6Скоринг по рубрике → грейд

Итог — не бинарная метка, а балл по критериям, отображённый на шкалу грейдов с доверительным интервалом.28

Правила смены грейда: грейд не понижается принудительно — после неуспеха доступен тест на уровень ниже; успешный кандидат может повысить грейд. Любая смена ограничена по времени (значение по умолчанию — 3 месяца). Первичное присвоение грейда сменой не считается.

Регулярные короткие задания: система периодически предлагает кандидату задачу от работодателя — решить или предложить подход. Это поддерживает профиль в актуальном состоянии и даёт работодателю свежий сигнал. Прокторинг доступен на рынке РФ.25

06Механика подбора и объяснимость

Прозрачная взвешенная функция ранжирования; каждый кандидат в подборке получает обоснование попадания.

score = w1 · test_strength        # сила подтверждённого профиля
      + w2 · fsp_achievements     # подтверждённые достижения ФСП
      + w3 · freshness            # активность в регулярных заданиях
      + w4 · semantic_fit         # соответствие потребности (эмбеддинги)

Критерии и веса фиксируются до просмотра пула; отсутствующие данные не додумываются; аудит высоких, средних и низких рангов.1011

Пример evidence-trail

  • Тест на грейд middle пройден с оценкой θ = 0.72
  • Подтверждено 2 достижения: призёр регионального чемпионата (2025), финалист всероссийской олимпиады (2024)
  • Решил 3 задания работодателей за последний месяц
  • Совпадение стека по потребности: Python, PostgreSQL, Docker

Такой же принцип — при «нет истории ФСП»: блок явно помечается как «нет данных», без додумывания.

07Обязательные правила данных и видимости

Реализуются сервисным слоем политик — это требования, а не пожелания.

1Зарплата обязательна

И в вакансии, и в приглашении — диапазон «от–до», в рублях. Кандидат видит условия до начала общения.

2Контакты скрыты

Работодатель не видит контакты кандидата до момента принятия приглашения или самостоятельного отклика.

3Статусы

Приглашения и отклики имеют статусы (отправлено, просмотрено, принято, отклонено); обе стороны видят актуальный статус.

4Регистрация по email

С подтверждением адреса. Верификация компании и модерация вакансий на MVP не требуются — это вне рамок MVP.

08Сценарии использования: полный разбор

Какие маршруты есть у каждой роли и чем они подтверждены в ТЗ. Полная версия с матрицей требований и маршрутом демонстрации — в docs/07-scenarios.md.

AМаршруты соискателя

Регистрация с согласиями→ Подтверждение адреса→ Профиль: форма / PDF / разбор моделью→ Опрос по специализации→ Выбор предполагаемого грейда→ Адаптивный тест 10–16 заданий→ Авто-категория (специализация × грейд)→ Приглашения: принять / отклонить→ Отклик на вакансию (доп.)→ Регулярные задания→ Приватность и связь с ФСП

Ветвления, каждое обработано: незавершённый тест продолжается на том же задании; после неуспеха доступен тест на уровень ниже (грейд не понижается принудительно); смена грейда ограничена 90 днями; профиль без истории ФСП остаётся корректным; истёкшая сессия продлевается или явно сообщает о себе.

BМаршруты работодателя

Регистрация и профиль компании→ Описание потребности→ Подборка с объяснением по каждому→ Уточнение без потери прежней версии→ Поиск по банку с фильтрами→ Приглашение с зарплатой→ Статусы и отзыв приглашения→ Контакты после принятия→ Публикация и правка вакансии→ Отклики: принять / отклонить→ Короткие задания кандидатам

Ключевое отличие: инициатива у работодателя — он находит нужную категорию и сам выходит на конкретного человека. Вакансия для этого не обязательна: приглашение можно направить напрямую из подборки или поиска.

Почему так

Разделение слоёв и слабо связанные модули — по требованиям; при необходимости модули выделяются в сервисы без переписывания логики.

Mock-first

LLM, реестр ФСП, почта, хранилище, прокторинг — за интерфейсами. Демо воспроизводимо оффлайн, без внешних сервисов.

Совместимость с Keycloak

Аутентификация через абстракцию AuthProvider: локальная реализация (LocalAuthProvider) заменяется на KeycloakAuthProvider (OIDC-токены realm + проверка подписи id_token по JWKS) без изменения бизнес-логики.

ИИ-слой: локальная открытая модель — подробно в разделе 09

Модель работает локально

Любая открытая модель через Ollama — например Gemma 4 (лицензия Apache 2.0, MoE 26B ≈ 4B активных параметров, контекст до 256K, 140+ языков), а также Qwen, Llama, Mistral. Тексты резюме не покидают контур: требование 152-ФЗ соблюдено, внешние ключи и квоты не нужны. Модель подбирается автоматически из установленных.

Что автоматизируется

Разбор резюме и профиля, черновик описания потребности, текст приглашения, сопроводительное письмо, объяснение попадания кандидата в подборку словами, заготовка короткого задания, семантическое сопоставление через эмбеддинги. ИИ только ускоряет рутину и не подменяет ядро: грейд присваивает тест, веса ранжирования фиксированы.

Демо работает без модели

Если модели нет, платформа не ломается: те же функции отвечают детерминированными демо-данными за 10–20 мс и помечают ответ degraded=true. Интерфейс честно показывает «ИИ: демо-режим» и не выдаёт это за работу модели. Замеры на реальной Gemma 4 и особенности модели — docs/06-ai.md.

10ИИ-слой: что делает модель и почему локально

Дополнительный функционал сверх ТЗ. Открытая модель выполняет рутинные текстовые операции и семантическое сопоставление, но ядро решения не подменяет: грейд присваивает тест, веса ранжирования фиксированы. Все семь функций вызываются из интерфейса обеих ролей — не только из API.

Модель и почему именно такая

Gemma 4 — что это по факту

Открытая модель Google под лицензией Apache 2.0: разрешительная, без ограничений на коммерческое использование. Смесь экспертов MoE 26B ≈ 4B активных параметров — качество крупной модели при скорости небольшой; контекст до 256K токенов, поддержка 140+ языков включая русский. Такое сочетание закрывает требование ТЗ об открытом коде и разрешительных лицензиях.3132

Модель не прибита гвоздями

Подключение через стандартный интерфейс Ollama: подойдут Qwen, Llama, Mistral и любая другая открытая модель — при старте система сама определяет, что установлено, и использует это. Код не знает о конкретной модели: работает абстракция провайдера, как и с остальными внешними сервисами.3335

Если модели нет — демо идёт

Те же семь функций отвечают детерминированными демо-данными за 10–20 мс и помечают ответ degraded=true. Интерфейс честно показывает «ИИ: демо-режим» и не выдаёт заглушку за работу модели. Поэтому демонстрация воспроизводима оффлайн — в том числе на машине судьи без установленной модели.

Замеры на реальной модели

Отключение режима рассуждений (think:false) сократило ответ на коротких задачах с 9.8 с до 0.25 с — при извлечении полей длинные рассуждения не нужны. Принудительный формат format:"json" убирает обёртку ответа в markdown: JSON разбирается без правок регулярками. Черновик потребности из русской заметки на реальной модели — около 8 с.

Чего ИИ не делает

Не присваивает грейд, не меняет веса ранжирования, не ранжирует кандидатов сам и не принимает решений о найме. Позиция в подборке — результат фиксированной рубрики; модель объясняет и ускоряет, но на порядок выдачи не влияет.

Как переключить

Переменные окружения: LLM_PROVIDER (auto | ollama | mock), OLLAMA_BASE_URL, OLLAMA_MODEL (пусто — автоподбор), SEMANTIC_MATCH_ENABLED. Состояние видно в интерфейсе и на /api/v1/ai/status. Замеры и детали — docs/06-ai.md.

Три режима. auto — использует реальную модель, при её недоступности уходит в демо-режим; ollama — только реальная модель; mock — всегда демо-данные (нужно автотестам и оффлайн-демонстрации). Значок в интерфейсе честно показывает, что работает сейчас: «ИИ: локальная модель» или «ИИ: демо-режим».

11Кабинет администратора и подсказки

Сверх обязательного объёма ТЗ: наблюдение за платформой как за двусторонним рынком и инструменты, снижающие ручную работу. Обязательный путь кандидата и работодателя при этом не меняется — раздел только наблюдает и подсказывает. Подробности: docs/08-admin.md.

Состояние рынка

Число пользователей ничего не говорит о двустороннем рынке: он может быть многолюдным и мёртвым. Поэтому измеряем ликвидность — долю потребностей, доведённых до приглашения, — а также воронку пути кандидата, соотношение сторон, время до первого ответа и баланс спроса и предложения по категориям.

Схема взаимодействия

Кто с кем взаимодействует: компании слева, соискатели справа, линия — приглашение, цвет — статус (отправлено / просмотрено / принято / отклонено / отозвано). Видно и активные компании, и полученные ответы, и отозванные предложения.

Дашборды обоих кабинетов

Сводка есть и у соискателя, и у компании — вкладка «Обзор» открывается первой. У соискателя: заполненность профиля, категория, оценка θ, приглашения по статусам, свои отклики. У компании: потребности и подборки, приглашения по статусам, доля ответов, открытые вакансии. Пустые значения честно показываются как «нет данных», а не как ноль.

Сигналы, требующие внимания

Не «предсказания», а следствия данных: потребности без подборки, приглашения без ответа дольше недели, компании без приглашений, кандидаты без категории, повторяющиеся названия компаний, дефицит кандидатов в категориях.

AПодсказки кандидату

Если человек выбирал вакансии — платформа ищет похожие на них; если откликов ещё нет — опирается на профиль и присвоенную категорию. У каждой вакансии указано, почему она предложена: «совпадают специализация и грейд», «совпадает стек: python, postgresql».

выбранные вакансии+ профиль и категория→ близкие вакансии с причинами

BПодсказки компании

Опора — действия компании: описанные потребности, их стеки и те, кого она уже приглашала. Уже приглашённые не повторяются — ручная работа не дублируется. Причины указываются у каждого кандидата: «точно та категория, которую вы описали», «похож на тех, кого вы приглашали».

потребности+ прошлые приглашения→ кандидаты с причинами
Про «дообучение» — честно: модель не дообучается. Ранжирование строится на сигналах, накопленных платформой о конкретном пользователе, плюс семантическая близость через эмбеддинги. Так результат объясним (видно каждую причину) и воспроизводим. ИИ в кабинете администратора не считает метрики: ему передаются уже посчитанные числа, а он связывает их словами — придумать показатель модель не может.

Валидация нашла дефекты — и они исправлены

Первый прогон дал Precision@5 = 0.25 и стабильность грейда 61%. Причина: выдача ранжировалась только по баллу, поэтому сильный кандидат «не той» категории обходил подходящего; тест был слишком коротким (6–12 заданий на шкалу из 6 грейдов). После исправлений — порядок «категория → сила профиля», минимум 10 заданий, банк расширен с 66 до 144 заданий с равномерным покрытием сложности — Precision@5 вырос в 2.7 раза. Ограничения зафиксированы честно: разметка составлена командой, рост точности дальше требует эмпирической калибровки банка.

Куда направлены усилия: два ядра закрывают 60% оценки.

Новая механика подбора35%
Тестирование, валидация, категоризация25%
Удобство интерфейса10%
Питч-сессия10%
Техническая проработка7%
Дополнительный функционал7%
Полнота реализации и документация6%

Чем закрываем

  • Подбор (35%) — подборка, ранжирование, объяснимость, приглашение без привязки к вакансии
  • Тестирование (25%) — гибридная механика, лимит смены грейда, процедура валидации с числами
  • Интерфейс (10%) — единый понятный сквозной путь в обоих кабинетах
  • Техника (7%) — архитектура, Docker, OpenAPI, скорость, тесты
  • Полнота (6%) — обязательные шаги, ветка без ФСП, документация
  • Доп. функционал (7%) — отклики/вакансии, регулярные задания, антифрод/ATS, адаптив

17Запуск и демонстрация: пошаговая инструкция

Инструкция рассчитана на человека без технического опыта: что установить, как запустить одной командой, что нажимать в демонстрации и что должно появиться на экране.

1Что нужно

Компьютер (macOS, Windows или Linux), 8 ГБ оперативной памяти (комфортно 16 ГБ), около 6 ГБ свободного места и бесплатная программа Docker Desktop. Больше ничего устанавливать не требуется: база данных, сервер приложения и веб-интерфейс поднимаются сами внутри Docker.

2Нужен ли интернет

Только при первом запуске — скачать программу и образы. Дальше демонстрация работает полностью оффлайн: все внешние сервисы (LLM, реестр ФСП, почта, файловое хранилище) заменены встроенными mock-реализациями.

3Сколько времени

Установка Docker — 5–10 минут. Первый запуск платформы — 3–7 минут (идёт сборка образов). Каждый следующий запуск — несколько секунд.

Шаг 1. Установить и запустить Docker Desktop

ДействиеКак именноПризнак, что получилось
Скачать Открыть docker.com/products/docker-desktop и нажать кнопку скачивания для своей системы Файл установщика скачан в «Загрузки»
Установить macOS: открыть скачанный файл и перетащить Docker в папку «Программы». Windows: запустить установщик и следовать подсказкам (согласиться со значениями по умолчанию) Docker появился в списке приложений системы
Запустить Открыть Docker Desktop как обычную программу и дождаться зелёного статуса «Docker Desktop is running» (30–60 секунд) В строке меню (macOS) или в трее (Windows) виден значок кита
Важно: Docker Desktop должен быть запущен всё время, пока вы работаете с платформой. Если он закрыт, команды ниже выдадут ошибку «Cannot connect to the Docker daemon» — в этом случае просто запустите Docker Desktop и повторите команду.

Шаг 2. Открыть терминал

macOS

Нажать ⌘ + Пробел (поиск Spotlight), набрать Терминал, нажать Enter. Откроется окно с командной строкой.

Windows

Нажать Пуск, набрать PowerShell, нажать Enter. Откроется окно с командной строкой.

Все следующие команды вводятся в это окно: строку копируют целиком, вставляют и нажимают Enter. После выполнения команда снова «приглашает» ввод — значит, она завершилась и можно вводить следующую.

Шаг 3. Запустить платформу

Сначала перейти в папку с проектом (подставьте свой путь к папке project):

cd путь/к/папке/moscow_it_pratform_test/project      # macOS и Linux
cd путь\к\папке\moscow_it_pratform_test\project      # Windows
Подсказка: путь удобно не набирать вручную. Наберите cd (с пробелом), затем перетащите папку project из окна Finder (macOS) или Проводника (Windows) прямо в окно терминала — путь подставится сам — и нажмите Enter.

Затем — одна команда, которая собирает и запускает всё решение:

docker compose up -d --build

Первый запуск идёт 3–7 минут: скачиваются и собираются образы, в окне бегут строки логов. Это нормально. Когда управление вернётся и появится приглашение ввода — платформа запущена.

Схему базы создаёт сам контейнер API: миграции применяются автоматически перед запуском сервера, отдельная команда не нужна.

Проверить, что поднялись все четыре сервиса:

docker compose ps

В таблице должно быть четыре строки со статусом Up … (healthy): backend, db, frontend, redis. Если у backend ещё написано (health: starting) — подождите 20–30 секунд и повторите команду; база данных стартует чуть дольше остальных.

Шаг 4. Открыть платформу в браузере

Шаг 6. Сценарий демонстрации: что нажимать

Полный смысл продукта виден в двух кабинетах: работодатель находит категорию и приглашает, кандидат получает приглашение с зарплатой. Ниже — по шагам, что делать и что должно появиться на экране.

Работодатель: hr@fintech-demo.ru

  1. Войдите под аккаунтом работодателя. Откроется «Кабинет работодателя» с вкладками «Подбор кандидатов», «Поиск по банку», «Приглашения», «Профиль компании».
  2. На вкладке «Подбор кандидатов» заполните потребность: название роли, специализация, грейд, стек. Нажмите «Сформировать подборку».
  3. Появится список кандидатов с позицией, баллом и раскрытыми причинами попадания («Подтверждённый профиль», «Совпадение стека»), а также блоком «нет данных» там, где информации действительно нет. Контактов в списке нет — вместо них подпись «Контакты скрыты до принятия приглашения».
  4. Нажмите «Уточнить подборку» — создастся новая версия, а прежняя останется в блоке «История подборок» с пометкой «уточнение предыдущей версии». Ничего не теряется.
  5. Откройте вкладку «Поиск по банку», задайте фильтры (специализация, грейд, стек, наличие достижений ФСП) и нажмите «Найти».
  6. У любого кандидата нажмите «Пригласить», укажите зарплату (поле обязательное) и текст предложения, затем «Отправить приглашение».
  7. На вкладке «Приглашения» виден статус отправленного приглашения. Контакты кандидата появятся здесь только после того, как он его примет.

Кандидат: anna.kovaleva@demo.ru

  1. Нажмите «Выйти» и войдите под аккаунтом кандидата. Откроется «Кабинет соискателя»: «Категория и грейд», «Тестирование», «Приглашения», «Профиль и ФСП».
  2. На вкладке «Категория и грейд» видно присвоенную категорию (специализация × грейд), историю смены грейда и историю тестирования. Категория присвоена автоматически по тесту, а не выбрана из резюме.
  3. На вкладке «Тестирование» пройдите обязательный путь: опрос по отрасли → выбор предполагаемого грейда → адаптивный тест (10–16 заданий, сложность подстраивается под ответы) → категория присваивается системой по итогу.
  4. На вкладке «Приглашения» — приглашение от компании: название компании и зарплата видны до начала общения. При открытии вкладки статус приглашения меняется на «просмотрено». Нажмите «Принять» — только после этого работодатель получает ваши контакты.
  5. На вкладке «Профиль и ФСП» — профиль, загрузка PDF-резюме, настройки приватности и привязка идентификатора ФСП с подтверждёнными достижениями.

Отдельно стоит показать кандидата без истории ФСП: платформа честно помечает этот блок как «нет данных», а не додумывает достижения.

Шаг 7. Остановить платформу

docker compose down        # остановить; созданные данные сохранятся
docker compose down -v     # остановить и удалить данные (полный сброс)

Шаг 8. Чистая база перед показом

Сквозные проверки (scripts/smoke-*.sh) работают на том же стенде, что и демонстрация, поэтому после них в кабинетах остаются тестовые компании, вакансии и задания — они помечены словом [проверка], чтобы их нельзя было принять за реальные данные. Вернуть чистое состояние — одна команда:

bash scripts/reset-demo.sh

Скрипт пересобирает стек с нуля, дожидается готовности API и загружает демонстрационные данные. То же вручную: docker compose down -v → docker compose up -d --build → docker compose exec -T backend python scripts/seed_demo.py.

Проверки для технических судей

Все проверки воспроизводимы и выполняются в терминале. Окружение Python в репозиторий не входит (папка .venv исключена из git), поэтому создайте его один раз — это занимает минуту:

cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt

Дальше проверки запускаются так:

cd backend
.venv/bin/python -m pytest -q                                  # 253 теста
.venv/bin/python -m pytest -q --cov=app                        # покрытие 97%
.venv/bin/python scripts/validate_solution.py --runs 120       # метрики валидации
cd .. && bash scripts/verify-stack.sh                          # состояние всех сервисов

Проверки кода: cd backend && ruff check . && ruff format --check . — линтер проходит без замечаний. Всё то же доступно через make help в корне проекта.
