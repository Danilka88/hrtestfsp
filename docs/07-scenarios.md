# 07. Сценарии использования: полный разбор

Документ отвечает на три вопроса: **какие маршруты есть у каждой роли**, **что происходит
на каждом шаге** и **каким требованием ТЗ он задан**. Разбор составлен сверкой с работающим
стендом (58 методов API), а не с замыслом: каждый сценарий ниже проверен на живой системе.

Обозначения: **A** — сценарии соискателя, **B** — работодателя, **X** — сквозные правила.
В конце — матрица требований и маршрут демонстрации для жюри.

---

## Роли и точки входа

| Роль | Вход | Что видит |
|---|---|---|
| Соискатель | `/login` → `/candidate` | свой профиль, тестирование, приглашения, вакансии, задания, ФСП |
| Работодатель | `/login` → `/employer` | потребность, подборка, поиск по банку, приглашения, вакансии, задания, профиль компании |
| Гость | `/` (лендинг), `/health` | описание решения и состояние сервиса |

Разделение прав обеспечивается ролью в токене: кандидат не может вызвать методы
работодателя и наоборот (проверено тестами: `403` при несовпадении роли).

## A. Маршруты соискателя

### A1. Регистрация и вход

1. Регистрация по электронной почте с согласием на обработку персональных данных
   (обязательно) и на публикацию профиля (опционально).
2. Подтверждение адреса. В демонстрационном режиме письмо не отправляется — код
   подтверждения показывается в интерфейсе, чтобы путь проходился целиком офлайн.
3. Вход. Сессия продлевается автоматически по refresh-токену; если продлить нельзя —
   вывод «Сессия истекла — войдите заново» и возврат на экран входа.

*Требование ТЗ: §2.2(4) регистрация с подтверждением адреса, согласия (§3.5).*
*Реализация: `POST /auth/register`, `POST /auth/verify-email`, `POST /auth/login`, `POST /auth/refresh`.*

### A2. Профиль: три способа заполнения

| Способ | Когда удобен | Что делает система |
|---|---|---|
| Вручную по форме | данных немного | сохраняет поля профиля |
| Загрузка PDF-резюме | резюме уже есть | извлекает ФИО, контакты, стек, грейд, роли, стаж, софт-скиллы |
| Разбор текста моделью | резюме в свободной форме | уточняет поля и переносит их в форму для проверки |

Отдельно: **стандартизированный PDF-профиль** — выгрузка профиля в едином виде, чтобы
работодатель сравнивал кандидатов по одинаковой структуре, а не по вёрстке чужих резюме.

*Требование ТЗ: §2.1 кандидат — «заполнение профиля и резюме … автогенерация PDF».*
*Реализация: `PUT /candidates/me/profile`, `POST /candidates/me/resume`, `GET /candidates/me/profile/pdf`, `POST /ai/profile/analyze`.*

### A3. Обязательный путь: опрос → грейд → тест → категория

Это ядро категоризации: работодатель видит не самоописанное резюме, а результат проверки.

1. **Опрос** по отрасли и специализации.
2. **Выбор предполагаемого грейда** — заявляет сам кандидат, но подтверждается тестом.
3. **Адаптивный тест** (10–16 заданий). Сложность следующего задания выбирается по текущей
   оценке θ: тест уточняет уровень, а не перебирает вопросы подряд.
4. **Автоматическое присвоение категории** — связка «специализация × грейд».
5. **Регулярные короткие задания** — поддерживают профиль в актуальном состоянии.

Особые случаи, каждый обработан явно:

- **незавершённый тест** — прогресс сохраняется; возврат продолжает тест ровно с того
  задания, которое было предъявлено (иначе после перерыва подбор выдал бы другой вопрос);
- **тест ниже заявленного грейда** — грейд не понижается принудительно: кандидат может
  пройти тест на уровень ниже;
- **повышение грейда** — ограничено 90 днями между сменами;
- **нет истории ФСП** — профиль формируется без достижений, блок ФСП честно пуст.

*Требование ТЗ: §2 (обязательный путь, отказ от принудительного понижения, лимит смены
грейда), §2.1, §2.3(0).*
*Реализация: `POST /testing/survey`, `GET /testing/grades`, `GET /testing/specializations`,
`POST /testing/sessions`, `POST /testing/sessions/{id}/answers`, `GET /testing/me/category`.*

### A4. Приглашения от работодателей — основная механика

1. Кандидат получает приглашение с названием компании, описанием предложения и
   **диапазоном зарплаты до начала общения**.
2. Открытие приглашения переводит его в статус «просмотрено» — работодатель видит интерес.
3. **Принять** → контакты кандидата раскрываются работодателю.
   **Отклонить** → контакты остаются скрытыми.
4. Если работодатель отозвал приглашение, кандидат видит «отозвано работодателем» и
   подсказку проявить инициативу самому.

*Требование ТЗ: §2.2(1,2,3), ключевая механика §2.*
*Реализация: `GET /candidates/me/invitations`, `POST .../view`, `POST .../decision`.*

### A5. Самостоятельный отклик (дополнительный сценарий)

Кандидат, не получивший приглашений, сохраняет возможность проявить инициативу:
список опубликованных вакансий → отклик с сообщением → статус отклика → при принятии
отклика контакты раскрываются работодателю.

*Требование ТЗ: §2.1 кандидат — «просмотр вакансий и отклик» (желательно), §6.6.*
*Реализация: `GET /candidates/me/vacancies`, `POST .../applications`, `GET /candidates/me/applications`.*

### A6. Настройки и приватность

- Приватность: что видно работодателю (стек, стаж, достижения ФСП, контакты в PDF).
- Согласия: обработка персональных данных и публикация профиля.
- Связь с ID участника ФСП: указать, обновить, отвязать.

*Требование ТЗ: §2.1 кандидат — «настройки», §3.5 (152-ФЗ).*
*Реализация: `PATCH /candidates/me/privacy`, `PATCH /auth/consents`, `GET|PUT /candidates/me/fsp`.*

## B. Маршруты работодателя

### B1. Регистрация и профиль компании

Регистрация по почте, затем описание организации: название, направление, сайт, контакт.
Профиль компании подставляется в приглашения, чтобы кандидат понимал, кто его зовёт.

*Требование ТЗ: §2.1 работодатель — «профиль компании».*
*Реализация: `GET|PUT /employers/me/profile`.*

### B2. Описание потребности → подборка

1. **Потребность**: кого ищут, чем занимается команда, стек, специализация, грейд, зарплата.
2. По желанию — **черновик описания моделью** из короткой заметки.
3. **Подборка**: рекомендованные категории и конкретные кандидаты.
4. **Объяснение по каждому кандидату**: вклад каждого критерия в балл, позиция в подборке,
   явная пометка критериев без данных («не оценено: результат теста — вклад 0»).
5. **Уточнение запроса** без потери прежней подборки: каждая версия хранится отдельно.

*Требование ТЗ: §2.1 работодатель — «описание потребности», «работа с подборкой»; §2.2
функциональные требования к поиску и подбору.*
*Реализация: `POST /employers/me/needs`, `POST /employers/me/selections/{id}/refine`,
`GET /employers/me/selections`, `POST /ai/need/draft`, `POST /ai/match/explain`.*

### B3. Поиск по банку кандидатов

Доступ ко всей базе с фильтрами: специализация, грейд, стек, наличие подтверждённых
достижений ФСП. Карточка показывает подтверждённый профиль, но **не контакты**.

*Требование ТЗ: §2.1 работодатель — «поиск по банку кандидатов».*
*Реализация: `GET /employers/me/search`.*

### B4. Выход на контакт — ядро продукта

1. **Приглашение конкретному кандидату**: описание предложения, зарплата (обязательна),
   название компании, способ связи. Привязка к опубликованной вакансии не требуется.
2. По желанию — **черновик текста приглашения моделью**.
3. **Отслеживание статусов**: отправлено → просмотрено → принято / отклонено.
4. **Отзыв приглашения**, пока кандидат не принял решение: отправленное по ошибке
   предложение не остаётся висеть на кандидате, а работодатель может отправить новое.
5. **Получение контактов** — только после принятия приглашения кандидатом.

*Требование ТЗ: §2 (ключевой сценарий), §2.2(1,2,3).*
*Реализация: `POST /employers/me/invitations`, `GET /employers/me/invitations`,
`POST .../{id}/revoke`, `POST /ai/invitation/draft`.*

### B5. Публикация вакансий (дополнительный сценарий)

Публикация вакансии с обязательной зарплатой, **редактирование** опубликованной вакансии,
закрытие, просмотр входящих откликов и решение по каждому (принять / отклонить).
Закрытая вакансия — архив: правка запрещена, чтобы условия не менялись задним числом.

*Требование ТЗ: §2.1 работодатель — «публикация вакансий … с возможностью
редактирования, просмотра входящих откликов».*
*Реализация: `POST /employers/me/vacancies`, `PUT .../{id}`, `POST .../{id}/close`,
`GET .../{id}/applications`, `POST .../applications/{id}/decision`.*

### B6. Регулярные задания кандидатам (дополнительный сценарий)

Создание короткого задания от работодателя (с подсказкой модели), выдача кандидатам
подходящей категории, просмотр решений. Решение кандидата освежает дату активности
профиля — это свежий сигнал для работодателя.

*Требование ТЗ: §2 «регулярные короткие задания», §2.1, §6.6.*
*Реализация: `POST /employers/me/tasks`, `GET /employers/me/tasks`,
`GET .../{id}/submissions`, `POST /candidates/me/tasks/{id}/submissions`, `POST /ai/task/draft`.*

## X. Сквозные правила и состояния

| Правило | Как обеспечивается | Проверено |
|---|---|---|
| **X1. Контакты скрыты** до принятия приглашения или отклика | контакты отдаются только при статусе `accepted`, в остальных случаях — `null` | тест «контакты не раскрываются работодателю», «отказ оставляет контакты скрытыми» |
| **X2. Разграничение ролей** | роль в токене; чужой метод → `403` | тесты по каждому модулю |
| **X3. Изоляция данных** | кандидат видит только свои приглашения и отклики; работодатель — только свои записи | тесты «чужие приглашения», «чужие отклики», «чужая подборка» |
| **X4. Зарплата обязательна** | в вакансии и в приглашении; диапазон «от ≤ до» | тесты валидации зарплаты |
| **X5. Статусы видны обеим сторонам** | статус — часть записи, его видит и кандидат, и работодатель | сценарии A4, B4 |
| **X6. Отсутствующие данные не додумываются** | критерий даёт вклад 0 и не понижает позицию; в интерфейсе — пометка «не оценено» | тесты подбора, `docs/05-validation.md` |
| **X7. Отсутствие истории ФСП** | профиль формируется без достижений, блок ФСП честно пуст | тесты ФСП без истории |
| **X8. Деградация ИИ** | недоступная модель → демо-данные с пометкой `degraded`, сценарий не ломается | тесты устойчивости ИИ |
| **X9. Истёкшая сессия** | запрос повторяется после обновления токена; иначе явное сообщение и вход заново | проверено в браузере |

## Маршрут демонстрации для жюри

Сквозной путь на двух экранах, около 6 минут. Демо-доступ подставляется одной кнопкой на
экране входа (`bash scripts/reset-demo.sh` возвращает чистое состояние).

**Кандидат (2 мин):**
1. Войти как соискатель → раздел «Категория и грейд»: показать текущую категорию и пояснение θ.
2. «Тестирование» → начать тест → ответить на 2–3 задания → **уйти с раздела** (прогресс сохранён).
3. Вернуться: баннер «незавершённый тест» → «Продолжить тест» → **то же задание**, что было предъявлено.
4. Раздел «Приглашения»: показать предложение с зарплатой и кнопку решения.
5. «Профиль и ФСП»: связь с ID ФСП и приватность.

**Работодатель (3 мин):**
6. Войти как работодатель → «Подбор кандидатов»: сформировать подборку, показать объяснение
   попадания каждого кандидата и пометки «не оценено» у тех, у кого нет теста.
7. «Объяснить словами» у конкретного кандидата — модель формулирует причины ранжирования.
8. «Поиск по банку»: фильтр по специализации и достижениям ФСП.
9. «Приглашения»: отправить приглашение новому кандидату → показать статусы → **отозвать** его.
10. «Задания»: создать задание, показать выдачу кандидатам.

**Возврат к кандидату (1 мин):**
11. Принять приглашение → у работодателя **раскрылись контакты**. Это и есть главный тезис:
    контакт возникает по инициативе работодателя и только с согласия кандидата.
