# 03. План MVP

Цель — работоспособный прототип с **сквозным демонстрационным сценарием**,
воспроизводимо запускаемый одной командой и работающий оффлайн на seed-данных.

---

## 1. Границы MVP

### Обязательно (must)
- Регистрация по email с подтверждением, роли, RBAC, изоляция данных.
- Профиль кандидата: форма + загрузка PDF с автораспознаванием + генерация
  стандартного PDF-профиля.
- Опрос → выбор грейда → тест → **автоматическое присвоение категории**;
  история опроса и теста; ограничение частоты смены грейда.
- Кабинет работодателя: профиль компании → описание потребности → **подборка**
  кандидатов; поиск по банку с фильтрами; **объяснимость** выдачи.
- **Приглашение** кандидату с обязательной ЗП (диапазон), статусы приглашений,
  **сокрытие контактов** до принятия/отклика.
- Корректная обработка кандидата **без истории ФСП**.
- OpenAPI/Swagger, Docker-compose, сопроводительная документация,
  **демо-данные и seed-скрипт**.

### Желательно (should, добор баллов)
- Регулярные короткие задания от работодателей.
- Самостоятельный отклик кандидата на открытые вакансии и публикация вакансий.
- Адаптивная вёрстка для мобильных/планшетов.
- Проработанная концепция защиты от фиктивных вакансий и интеграции с ATS.

---

## 2. Этапы разработки

### Этап 0 — Каркас и инфраструктура
- Структура репозитория (`backend/`, `frontend/`, `seed/`, `docs/`).
- `docker-compose.yml`, `.env.example`, Dockerfile'ы.
- Каркас FastAPI (роутеры, зависимости, конфиг, health-check), Alembic.
- Каркас SPA (роутинг, layout, тема, API-клиент).
- **Результат:** `docker compose up` поднимает пустой, но живой сервис.

### Этап 1 — Аутентификация, роли, согласия
- Регистрация по email + подтверждение (мок-провайдер почты).
- Вход, JWT access/refresh, RBAC (`CANDIDATE`/`EMPLOYER`/`ADMIN`).
- Согласие на обработку и публикацию данных профиля (152-ФЗ), фиксация факта.
- Абстракция `AuthProvider` (готовность к Keycloak).
- **Результат:** регистрация/вход обеих ролей, разграничение доступа.

### Этап 2 — Профиль кандидата
- Заполнение профиля по форме.
- Загрузка PDF-резюме + автораспознавание (ФИО, контакты, стек, грейд, роли,
  стаж, софт-скиллы) через `LLMProvider` (мок — rule-based).
- Генерация стандартизированного PDF-профиля.
- Настройки приватности (что видно работодателю).
- **Результат:** профиль можно создать двумя способами и выгрузить PDF.

### Этап 3 — Тестирование и категоризация (ядро №1)
- Справочники: специализации, грейды, категории (= специализация × грейд).
- Опрос по отрасли/специализации; выбор предполагаемого грейда.
- Банк заданий: шаблоны + параметры сложности/дискриминативности, версии,
  лимиты показов (exposure).
- Адаптивная выдача заданий (упрощённая IRT) и оценка способности θ.
- Скоринг по рубрике → определение грейда и категории.
- Ограничение частоты смены грейда; тест ниже/выше уровня.
- Мониторинг аномалий (время ответа), нормализация под анти-плагиат кода.
- **Результат:** кандидат проходит путь опрос→тест→категория; правило смены грейда работает.

### Этап 4 — Подбор, поиск, ранжирование, объяснимость (ядро №2)
- Профиль компании и описание потребности работодателя.
- Формирование подборки: рекомендованные категории + кандидаты.
- Взвешенное ранжирование внутри категории (тест, ФСП, свежесть, семантика).
- **Evidence-trail** под каждого кандидата (объяснимость).
- Поиск по банку с фильтрами; сохранение подборки при уточнении запроса.
- **Результат:** работодатель по потребности получает объяснимую подборку.

### Этап 5 — Приглашения, статусы, отклики, ФСП
- Приглашение конкретному кандидату (описание, ЗП, компания, способ связи).
- Статусы `SENT → VIEWED → ACCEPTED | DECLINED`; видны обеим сторонам.
- Раскрытие контактов только после принятия/отклика (слой политик).
- Обработка профиля без истории ФСП.
- **Результат:** сквозной обратный сценарий «работодатель → приглашение → кандидат».

### Этап 6 — Дополнительный функционал
- Регулярные короткие задания: выдача, решение/подход, влияние на свежесть.
- Публикация вакансий + самостоятельный отклик кандидата.
- Адаптивная вёрстка.
- Концепция защиты от фиктивных вакансий и интеграции с ATS (документ + задел в коде).
- **Результат:** реализованы необязательные для MVP сценарии.

### Этап 7 — Демо, развёртывание, документация
- Seed-скрипт: реалистичные демонстрационные данные (кандидаты, работодатели,
  вакансии, приглашения, достижения ФСП — в т.ч. кандидат без истории ФСП).
- Сквозной демо-сценарий (см. §4), проверенный на оффлайн-запуске.
- Docker-развёртывание, README с пошаговым локальным запуском.
- Сопроводительная документация (doc/pdf) по составу из требований.
- Презентация (pptx/pdf).
- **Результат:** воспроизводимое демо + комплект документов.

### Этап 8 — Валидация решения
- Реализация собственной процедуры оценки и фиксация результатов (см. §5).
- **Результат:** раздел «валидация» в документации с числами.

## 4. Сквозной демонстрационный сценарий

1. **Регистрация соискателя** по email с подтверждением; согласие на обработку данных.
2. **Заполнение профиля**: форма или загрузка PDF с автораспознаванием; генерация
   стандартного PDF-профиля.
3. **Опрос → выбор грейда → тест**; показ адаптивной выдачи и уникальности заданий.
4. **Присвоение категории** (специализация × грейд) и отображение её кандидату.
5. **Кабинет работодателя**: описание потребности → **подборка** с объяснением
   попадания кандидатов.
6. **Выход на контакт**: приглашение с уровнем ЗП; кандидат видит **условия до
   начала общения**; принятие приглашения → **раскрытие контактов** работодателю.
7. Демонстрация **кандидата без истории ФСП** (корректная ветка «нет данных»).
8. *(Если реализовано)* **Классический отклик** кандидата на открытую вакансию.
9. Отдельно объясняются **механика тестирования** и **механика подбора**.

## 5. Собственная процедура валидации (план)

| Что проверяем | Метрика | Процедура |
|---|---|---|
| Релевантность подбора | Precision@5 / Precision@10 | Синтетический набор пар «потребность – кандидат» с ручной разметкой команды; доля релевантных в топе |
| Согласованность теста | Стабильность грейда при повторном прохождении | Повторные прохождения одними и теми же профилями в симуляции |
| Дискриминативность заданий | Разделение слабых/сильных | Сравнение с экспертной оценкой профилей; разброс θ по группам |
| Корректность категоризации | Доля верно отнесённых | Соответствие ручной разметке специализации/грейда |
| Устойчивость к утечке | Доля «засвеченных» заданий | Симуляция «обмена заданиями», срабатывание exposure-контроля и детекции аномалий |
| Обработка без ФСП | 100% корректных веток | Кандидат без `fsp_id` проходит весь путь без ошибок |

Метрики фиксируются скриптом и приводятся в документации с числами.

## 6. Трассировка на критерии оценки

| Критерий (вес) | Что закрывает |
|---|---|
| Новая механика подбора (35%) | Этапы 4–5: подборка, ранжирование, объяснимость, приглашение без привязки к вакансии, раскрытие контактов |
| Тестирование/валидация/категоризация (25%) | Этапы 3, 8: гибридная механика, ограничение смены грейда, процедура валидации с результатами |
| Интерфейс (10%) | Единый UX обоих кабинетов, понятный сквозной путь |
| Техническая проработка (7%) | Архитектура, Docker, OpenAPI, тесты, скорость |
| Полнота + документация (6%) | Этап 7: реализация обязательных шагов, ветка без ФСП, документация |
| Доп. функционал (7%) | Этап 6: отклики/вакансии, регулярные задания, антифрод/ATS, адаптив |
| Питч (10%) | Презентация + репетиция демо |

## 7. Риски и снятие

| Риск | Снятие |
|---|---|
| Переусложнение психометрики → не успеть | Упрощённая модель (порядок сложности + адаптивный отбор), без полной калибровки |
| Холодный старт (нет данных) | Seed-скрипт + синтетические демо-данные |
| Недоступность внешних сервисов | mock-провайдеры по умолчанию, оффлайн-демо |
| Скоуп-крип | Demo-first: сначала сквозной путь, потом доп. функции |
| Требования 152-ФЗ | Отдельное согласие, RBAC, Argon2, аудит, маскирование контактов |
| Лицензии зависимостей | Проверка лицензий (PyMuPDF — AGPL), при необходимости замена |
