# 01. Архитектура решения

## 1. Обзор

Веб-сервис с явным разделением на три слоя: **Frontend** (SPA для двух ролей),
**Backend** (API бизнес-логики) и **слой хранения** (реляционная СУБД +
кэш/очереди + объектное хранилище файлов). Внутри бэкенда — модульный монолит с
чётким разделением ответственности, что соответствует требованиям к архитектуре и
позволяет при необходимости выделить модули в микросервисы.

```
┌──────────────────────────────────────────────────────────────────────┐
│                          Браузер (desktop/mobile)                     │
│             Кабинет кандидата        │        Кабинет работодателя    │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ HTTPS / REST (JSON), OpenAPI
                    ┌───────────▼────────────┐
                    │   Frontend (SPA, nginx)│   React + TS + Vite
                    └───────────┬────────────┘
                                │ /api/v1/*
        ┌───────────────────────▼────────────────────────────────────┐
        │                      Backend (FastAPI)                     │
        │  ┌──────────┬───────────┬───────────┬───────────┬────────┐ │
        │  │  Auth    │ Candidate │ Employer  │  Testing  │Matching│ │
        │  │  & RBAC  │  Profile  │  Cabinet  │  Engine   │& Rank  │ │
        │  └──────────┴───────────┴───────────┴───────────┴────────┘ │
        │  ┌──────────────────────── Providers ─────────────────────┐ │
        │  │ LLM · FSP · Email · Storage · Code-similarity (моки)   │ │
        │  └────────────────────────────────────────────────────────┘ │
        └───────┬───────────────┬───────────────┬────────────────────┘
                │               │               │
        ┌───────▼──────┐ ┌──────▼──────┐ ┌──────▼───────┐
        │ PostgreSQL 16│ │  Redis 7    │ │ Файлы (том)  │
        │  + pgvector  │ │ кэш/сессии  │ │ RESUMES/PDF  │
        └──────────────┘ └─────────────┘ └──────────────┘
```

**Принцип MVP (demo-first).** Все внешние зависимости вынесены за интерфейсы
(`providers/`) с обязательной **mock-реализацией**. Демонстрационный сценарий
работает оффлайн, без интернета и внешних сервисов, на seed-данных.

## 2. Компоненты бэкенда (модули)

| Модуль | Ответственность |

| `items` | Банк заданий: шаблоны, параметры сложности, версии, счётчики показов (exposure) |
| `matching` | Формирование подборок, поиск по банку, ранжирование, объяснимость |

| `admin` | Управление справочниками (специализации/грейды), банк заданий, служебное |

## 3. Ключевая механика №1 — тестирование (ядро)

**Цель:** уникальные задания у каждого кандидата **и** сопоставимая сложность
между кандидатами одновременно.

**Решение — гибрид «генерация + калибровка»:**

1. **Параметрическая генерация.** Задание описывается шаблоном и параметрами
   (например, тема, входные данные, ожидаемый ответ). Из шаблона генерируется
   уникальный вариант; сложность задаётся **параметрами**, а не текстом.
2. **Адаптивная выдача.** Оценка способности (θ) обновляется после каждого ответа;
   следующее задание выбирается как максимизирующее информацию при текущей θ
   (упрощённая IRT/Раш-модель с параметрами сложности и дискриминативности).
3. **Item exposure control.** У каждого задания — лимит показов и счётчик; выбор
   со взвешиванием по остаточному «запасу», ротация версий.
4. **Детекция компрометации.** Мониторинг **времени ответа** и паттернов по
   заданию; при аномалии задание уходит на пересмотр, аномальные сессии — на
   ручную проверку.
5. **Анти-плагиат кода.** Для задач с кодом — сравнение по нормализованным
   токенам/AST между сессиями.
6. **Скоринг по рубрике.** Итог теста — не бинарная метка, а оценка по критериям →
   отображение на шкалу грейдов с порогами и доверительным интервалом.

**Правила смены грейда:** грейд не понижается принудительно; после неуспеха
доступен тест на уровень ниже; успешный кандидат может повысить грейд. Любая
**смена** грейда ограничена по времени (интервал — параметр конфигурации,
значение по умолчанию — 3 месяца). Первичное присвоение грейда сменой не считается.

**Регулярные короткие задания:** система периодически предлагает кандидату задачу
от работодателя; результат обновляет «свежесть» профиля и влияет на ранжирование.

## 4. Ключевая механика №2 — подбор и объяснимость

**Обратный подбор:** работодатель описывает потребность (стек, специализация,
грейд, чем занимается команда) → система формирует **подборку** — рекомендованные
категории и конкретных кандидатов.

**Ранжирование внутри категории** (прозрачная взвешенная функция):

```
score = w1 · test_strength        # сила подтверждённого профиля (оценка теста)
      + w2 · fsp_achievements     # подтверждённые достижения ФСП
      + w3 · freshness            # активность в регулярных заданиях
      + w4 · semantic_fit         # семантическое соответствие потребности
```

**Объяснимость.** Каждый кандидат в подборке получает **evidence-trail**: по
каждому компоненту score формируется человекочитаемое обоснование («тест на
грейд middle пройден с оценкой θ=…», «подтверждено 2 достижения ФСП», «решил 3
задания за последний месяц»). Критерии и веса **фиксируются до просмотра пула**,
отсутствующие данные не додумываются.

**Поиск по банку:** фильтры по специализации, грейду, категории, стеку, наличию
подтверждённых достижений ФСП. Уточнение запроса **не теряет ранее полученную
подборку** (подборка — сохраняемая сущность `Selection`).

## 6. Правила видимости и приватность (обязательные)

Реализуются **сервисным слоем политик** (не сериализацией «как получится»):

1. **ЗП обязательна** в вакансии и в приглашении — диапазон «от–до», в рублях.
2. **Контакты кандидата скрыты** от работодателя до момента, когда кандидат
   принял приглашение или откликнулся сам. До этого API отдаёт маскированное
   представление.
3. **Изоляция кандидатов**: кандидат видит только свои приглашения/отклики.
4. Статусы видны обеим сторонам по своим записям.
5. **152-ФЗ**: отдельное согласие на обработку и публикацию данных профиля,
   фиксация факта согласия; RBAC; безопасное хранение паролей (Argon2) и токенов.

## 7. Аутентификация и совместимость с Keycloak

На MVP — собственная аутентификация (email+пароль, подтверждение почты, JWT
access/refresh) за абстракцией `AuthProvider` (`app/providers/auth.py`):

- `LocalAuthProvider` — **активна по умолчанию**: сверяет Argon2-хэш и выпускает
  собственные токены; refresh регистрируется по `jti`, чтобы токен можно было
  отозвать;
- `KeycloakAuthProvider` — **реализована** как задел под ФСП ID: обменивает
  учётные данные на токены realm (`/protocol/openid-connect/token`) и проверяет
  подпись `id_token` по JWKS Keycloak; в MVP не активна, потому что развёрнутого
  realm ФСП на хакатоне нет.

Переключение — настройкой `AUTH_PROVIDER=local|keycloak`. Обе реализации приводят
результат к `ExternalIdentity`, поэтому сервисный слой (`app/services/auth.py`) и
API не знают, какая из них работает: при переходе на ФСП ID бизнес-логика не
меняется. Провайдеру передаётся уже загруженная запись пользователя — сам он в БД
не ходит, поэтому подменяется и тестируется изолированно.

## 8. Интеграция с реестром ФСП

- Интерфейс `FspProvider` с методами: `link(fsp_id)`, `fetch_achievements(fsp_id)`,
  `health()`.
- Реализации: `MockFspProvider` (демо, синтетические достижения) и заглушка для
  реального подключения.
- Профиль кандидата **всегда** корректно работает при `fsp_id = null` /
  отсутствии достижений: соответствующие блоки интерфейса и ранжирования явно
  помечаются как «нет данных», без додумывания.

## 9. Развёртывание

`docker-compose.yml` с сервисами: `db` (PostgreSQL + pgvector), `redis`,
`backend`, `frontend` (nginx), опционально `keycloak` (профиль `sso`).
Внешние зависимости (LLM/ФСП/email) по умолчанию — **мок-провайдеры**, включаются
переменными окружения. Пошаговая инструкция по локальному запуску — в README.

## 10. Слой ИИ и деградация

ИИ — **надстройка, а не зависимость**: основной путь (опрос → тест → категория →
подборка → приглашение) работает без модели. Слой ИИ ускоряет рутинные действия и
устроен так, чтобы демонстрация проходила на любой машине.

- **Локальная модель через Ollama.** Любая открытая модель (Gemma 4 — Apache 2.0,
  Qwen, Llama, Mistral): имя задаётся настройкой, при пустом значении модель
  выбирается автоматически из уже скачанных. Данные кандидатов не покидают контур
  (152-ФЗ), внешние ключи не нужны.
- **Деградация вместо отказа.** Режим `LLM_PROVIDER=auto` пробует модель, а при
  недоступности отдаёт детерминированные демо-данные и помечает ответ
  `degraded=true`. Интерфейс показывает источник явно; порядок релевантности
  сохраняется.
- **Границы применения.** ИИ не присваивает грейд (это делает тест), не
  выдумывает опыт и не влияет на веса ранжирования.

Подробности, замеры и инструкция по подключению модели — `docs/06-ai.md`.

## 11. Соответствие требованиям

| Требование | Как покрыто |
|---|---|
| Разделение FE / BE / хранение | SPA + FastAPI + PostgreSQL |
| Контейнеризация | Dockerfile + docker-compose |
| OpenAPI/Swagger | Автогенерация FastAPI (`/docs`, `/openapi.json`) |

| Keycloak-совместимость | Абстракция `AuthProvider` |
| Кроссплатформенность | Веб-сервис, независим от ОС при развёртывании |
| ML/NLP как преимущество | Разбор резюме, эмбеддинги для матчинга, генерация заданий |
| Обработка кандидата без ФСП | Явная ветка «нет данных» |
| Объяснимость выдачи | `reasons` в `SelectionCandidate` |
